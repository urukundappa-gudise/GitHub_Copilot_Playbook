# Disposable EC2/S3 Entra SSO E2E stack

This root is a temporary validation environment, not a replacement for the existing App Runner or ECS deployments. It has a separate Terraform state key under `e2e-sso/stacks/` and does not import, modify, or destroy shared resources.

## Operator prerequisites

Do not start until the operator confirms all of the following:

- An AWS account and region approved for temporary E2E use, with budget/cost monitoring enabled.
- An existing private S3 state bucket in the same region, with versioning, encryption, and all four public-access-block settings enabled. The bucket must have separate IAM permissions for state/registry and must not be deleted with the test stack.
- A dedicated GitHub Actions OIDC plan role and cleanup role. Trust only this repository's protected default branch and `sts.amazonaws.com`; do not use access keys. The plan role needs read/plan permissions and isolated state access. The cleanup role needs Terraform destroy permissions for this root's EC2/VPC/endpoints/NAT/ALB, RDS, S3, CloudFront/WAF, IAM, and Scheduler resources; S3 state/registry access only under `e2e-sso/stacks/*` and `e2e-sso/registry/*`; and `sns:Publish` scoped to the external alert topic. The operator apply identity needs corresponding create/read permissions and `iam:PassRole` only for the stack-specific `*-e2e-expiry-stop` role passed to EventBridge Scheduler. Validate both policies and OIDC trust before use.
- An Entra app registration with exact HTTPS redirect URI `https://<app-domain>/api/v1/auth/callback` and exact post-logout URI `https://<app-domain>/`. `AZURE_AD_CLIENT_SECRET` must exist in Secrets Manager; supply only its ARN. An RDS-managed master password is generated by AWS and is never placed in Terraform variables.
- The existing Infovision DNS administrator must manage `adlc.infovision.com` and `ai.adlc.infovision.com`; this Terraform root does not create or change Route 53 records. An ACM certificate covering both hostnames must be issued in `us-east-1` for CloudFront and the ALB. Add the ACM validation CNAMEs and, after apply, the app/API CNAMEs using the outputs below. Use a narrow client IPv4 CIDR allow-list. The API hostname must resolve to the ALB, whose security group accepts traffic only from CloudFront origin-facing addresses.
- An immutable ECR image tagged with the complete 40-character commit SHA, plus an SNS topic that remains outside the disposable stack and notifies the named owner.
- GitHub repository variables `E2E_AWS_REGION`, `E2E_STATE_BUCKET`, `AWS_E2E_PLAN_ROLE_ARN`, `AWS_E2E_CLEANUP_ROLE_ARN`, and `E2E_EXPIRY_ALERT_TOPIC_ARN`. Enable scheduled GitHub Actions. Restrict changes to the cleanup workflow and its IAM role.
- Explicit operator approval to create public HTTPS DNS names and incur short-lived CloudFront, WAF, ALB, EC2, NAT gateway, RDS, endpoint, data transfer, and logging charges. A single NAT gateway is needed for outbound HTTPS to Entra's OIDC endpoints; API security-group egress is limited to TCP 443. This repository does not apply the stack automatically.

If a prerequisite is unavailable, stop before registering the stack or running Terraform. Do not copy secret values into the sample JSON, shell history, chat, Terraform variables/state, AMI user data, or GitHub logs.

## Prepare, plan, and apply

Use a new stack ID for each attempt. Copy `terraform.tfvars.example.json` to a protected local file and replace every example value with approved non-secret settings and secret ARNs. Keep the file outside the repository. Set the app/API hosts to `adlc.infovision.com` and `ai.adlc.infovision.com`; set callback to `https://adlc.infovision.com/api/v1/auth/callback` and post-logout to `https://adlc.infovision.com/`. Entra registration and DNS records must agree exactly. If you cannot manage the existing Infovision DNS provider, ask its DNS owner to make these changes.

Before running `e2e-sso-prepare.ps1`, the ACM certificate must be `ISSUED`. To retrieve its DNS validation CNAMEs without displaying any secret, run:

```powershell
aws acm describe-certificate `
  --certificate-arn "<certificate-arn>" `
  --region us-east-1 `
  --query 'Certificate.DomainValidationOptions[].{Domain:DomainName,Name:ResourceRecord.Name,Type:ResourceRecord.Type,Value:ResourceRecord.Value}' `
  --output table --no-cli-pager
```

Ask the Infovision DNS owner to add those CNAMEs in the existing `infovision.com` DNS zone. The app/API CNAMEs are different: after apply, point `adlc.infovision.com` to `app_dns_cname_target` and `api.adlc.infovision.com` to `api_dns_cname_target`.

```powershell
aws sso login --profile <approved-operator-profile>
$env:AWS_PROFILE = '<approved-operator-profile>'
.\scripts\e2e-sso-prepare.ps1 `
  -ConfigPath 'C:\secure\e2e-sso-vars.json' `
  -StateBucketName '<private-state-bucket>'
```

The prepare script checks the operator identity and state-bucket controls, creates a unique state key, starts the 72-hour clock, and writes a secret-free expiry manifest before apply. It only stores non-secret configuration and ARNs. It does not apply or destroy. If Terraform apply fails partway, the registered manifest remains discoverable by the expiry runner.

Initialize and review the plan with the returned local variable file and state key:

```powershell
Set-Location deploy/ec2-s3-e2e
terraform init -input=false `
  -backend-config="bucket=<private-state-bucket>" `
  -backend-config="key=e2e-sso/stacks/<stack-id>/terraform.tfstate" `
  -backend-config="region=<state-bucket-region>" `
  -backend-config="use_lockfile=true" `
  -lockfile=readonly
terraform fmt -check
terraform validate
terraform plan -input=false -var-file '<temp-dir>\terraform.tfvars.json' -out '<temp-dir>\e2e.tfplan'
```

Review every planned resource, region, tag, CIDR, secret ARN, DNS record, state key, and expiry time. Only an authorized operator may apply the reviewed plan, after explicit approval:

```powershell
terraform apply '<temp-dir>\e2e.tfplan'
```

After apply, from the repository root build the React frontend and upload only `frontend/dist` to the output bucket. Then invalidate the distribution:

```powershell
npm ci --prefix frontend
npm run build --prefix frontend
$frontendBucket = terraform -chdir=deploy/ec2-s3-e2e output -raw frontend_bucket_name
$distributionId = terraform -chdir=deploy/ec2-s3-e2e output -raw cloudfront_distribution_id
aws s3 sync frontend/dist "s3://$frontendBucket" --delete
aws cloudfront create-invalidation --distribution-id $distributionId --paths "/*"
```

Never upload `.env`, source maps containing secrets, or local credentials. The EC2 bootstrap installs Docker, retrieves Entra and RDS credentials from Secrets Manager into a root-only `/run` file, runs the Alembic chain, then starts the immutable API image. Confirm migrations and `/health/live` before testing login.

Terraform outputs `app_dns_cname_target` and `api_dns_cname_target`. In the existing Infovision DNS provider, create CNAME records `adlc.infovision.com` -> `app_dns_cname_target` and `ai.adlc.infovision.com` -> `api_dns_cname_target`. Confirm both resolve publicly over HTTPS before starting the Entra flow. These DNS records are outside Terraform state; record their owner and remove them during teardown no later than the 72-hour expiry. The independent DNS-provider cleanup is an operator step, not automated by this AWS stack.

A plan-only GitHub workflow is available at `.github/workflows/e2e-sso-plan.yml`. It reads a prepared manifest and never applies. Protect the branch and OIDC role; do not broaden them to arbitrary pull requests.

## Automatic expiry and manual teardown

- The stack records creation/expiry metadata and tags stack-owned resources with `Purpose=e2e-sso`, `StackId`, `Owner`, and `ExpiresAt`.
- An EventBridge Scheduler action stops the exact EC2 instance at hour 68. CloudFront's viewer-request function returns `503` after hour 72, so the public app fails closed even when cleanup is delayed.
- `.github/workflows/e2e-sso-expiry.yml` scans the private registry every 15 minutes. At hour 68 it loads only the matching state key and manifest, runs `terraform destroy` with the recorded non-secret variables, keeps state for audit, and alerts through the external SNS topic on errors. Failed cleanup remains registered for retry.
- Before hour 68, or for an approved manual teardown, run `terraform destroy` from this root with the same backend key and variables. Verify the CloudFront distribution, ALB, EC2 instance, RDS database, VPC/endpoints, WAF resources, IAM role/profile, and frontend bucket are absent. Ask the Infovision DNS owner to remove the two external CNAMEs; Terraform cannot do this. Review S3 versions and the state/registry prefixes separately.

The EC2 stop and CloudFront cutoff are fail-closed controls, not proof of full AWS resource deletion. GitHub scheduled runners and AWS control planes can be delayed or unavailable. The 72-hour destruction criterion is not accepted until a disposable test stack has proved successful cleanup and a forced cleanup failure has proved alerting, retries, and inaccessible behavior. Keep the expiry workflow enabled and its external cleanup role valid until all manifests are cleared.
