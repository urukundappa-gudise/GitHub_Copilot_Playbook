Appendix D · Cross-client implementation patterns

Enterprise Identity Integration

A cross-client supplement to the GitHub-Native AI SDLC Playbook. Adapt the provider, callback URLs, cloud resources, and acceptance gates to each client’s approved environment.

Reference implementation status

The repository demonstrates a dedicated login entry, backend OIDC flow, deployment code, and CI/workflow controls. These are implementation patterns, not a deployed service or a client-specific configuration. Each client environment requires its own provider setup, deployment approval, live acceptance, and teardown proof.

Authentication path

A client application may provide a dedicated login entry such as /login. The browser navigates to a backend-owned authentication endpoint; provider secrets and tokens stay on the server.

Browser /login → GET /api/v1/auth/login → OIDC authorization-code flow + S256 PKCE → GET /api/v1/auth/callback → validated identity → opaque application session → GET /api/v1/auth/session

Identity and session

For Microsoft Entra ID, configure AZURE_AD_TENANT_ID, AZURE_AD_CLIENT_ID, AZURE_AD_REDIRECT_URI, and AZURE_AD_POST_LOGOUT_REDIRECT_URI. The backend discovers tenant-specific OIDC metadata and requests openid profile email. Validate issuer, audience, signature, expiry, state, nonce, and S256 PKCE; require the ID-token claims oid, upn, and name, with email optional. Use oid as the stable authorization subject, never email alone. Store only a digest of the opaque session token and set oidc_session as HttpOnly, Secure, and SameSite=Lax.

Authorization boundary

Production uses APP_ENV=production, AUTH_REQUIRED=true, and AUTH_MOCK_MODE=false. Keep AZURE_AD_CLIENT_SECRET server-side: local development reads it from the ignored .env; AWS ECS injects it from Secrets Manager by ARN. With authentication required, unauthenticated API and WebSocket requests fail closed. Logout revokes the local session before Entra sign-out. Mock identity is local/test-only and is never live provider acceptance evidence.

Human deployment gate

No workflow should automatically apply infrastructure or release an application artifact without an explicit authorization model. The operator builds and tags immutable artifacts, registers temporary-environment expiry, reviews the plan, obtains approval, applies, publishes only approved build output, and invalidates the CDN as required by the target platform.

Example isolated cloud topology

The following is one AWS mapping of the general controls, not a mandatory stack. Select equivalent managed services and boundaries for each client and cloud.

Application boundary

Private object storage behind a CDN and web application firewall; API compute in private subnets behind an HTTPS load balancer; managed PostgreSQL for identity transactions and sessions; managed remote administration; secret manager and workload identity for runtime secrets.

State and separation

Use a dedicated infrastructure root and unique state key per temporary environment. Do not import, modify, or destroy shared application resources. Keep externally owned DNS and state resources outside disposable stack scope.

CI should run infrastructure contract tests and formatting/validation alongside backend, migration, frontend, container, cloud-identity, and golden-evaluation gates. Complete migration and timing acceptance before release; use synthetic identities and never put production credentials in fixtures or logs.

Appendix D · Release readiness

Expiry, proof & open gates

Infrastructure code is not evidence that a deployment or teardown has succeeded. Keep every live acceptance gate open until it has been run in the target client environment.

Fail-fast governance and quality gates

Stage 1 defines mandatory gates and stop conditions; Stage 2 maps requirements to testable evidence, pass criteria, and owners. Stage 4 is the verification checkpoint: an Orchestrator Agent may coordinate deterministic checks and control phase transitions, but it must not invent or weaken criteria, accept its own remediation, or make deployment decisions. A failed or missing mandatory result blocks progression until remediation and revalidation are complete. Deployment approval remains a separate human decision in Stage 5.

Temporary-environment controls

  • Unique environment ID, isolated state, ownership/expiry tags, and secret-free registry manifest.
  • Schedule cleanup before expiry; a 72-hour lifetime is one example policy, not a universal default.
  • Fail closed at expiry if cleanup is delayed; alert and retain state for audit.
  • Prove successful cleanup and safe retries after a controlled failure.

Still requires operational proof

  • Successful cleanup of an applied disposable environment and complete cloud resource inventory check.
  • Controlled cleanup failure demonstrating alert, retry, and inaccessible behavior.
  • External resource owners remove DNS records by the agreed expiry deadline.
  • Retain Terraform state and sanitized CI evidence for audit.

Stage 4 · Verify: human-in-the-loop quality gate

Maintain a gate record for each required check: gate ID, source requirement, owner, command or review procedure, expected evidence, pass/fail rule, and remediation path. The orchestrator evaluates only declared deterministic results and presents evidence to the accountable human reviewer; it cannot mark a subjective or human-owned gate as passed on a person's behalf.

Fail-fast transition rules

  • Start a phase only when its required upstream gates are recorded as passed.
  • On a failed, skipped, stale, or missing mandatory result, set the phase to blocked and name the unmet criterion; do not launch dependent phases.
  • Create or route a traceable remediation task, preserve the original failure evidence, then rerun the failed check and affected regression gates.
  • Resume only after fresh evidence passes and the named reviewer records approval. There is no agent override or silent waiver path.

Human authority and boundaries

  • A human owner approves requirements, security exceptions, live identity-provider acceptance, and release readiness.
  • The orchestrator may schedule checks, collect sanitized evidence, block transitions, and request remediation; it cannot approve its own changes, merge, apply infrastructure, deploy, or suppress a failed gate.
  • Use branch protection, required CI checks, CODEOWNERS, stale-approval dismissal, and bypass restrictions where supported.
  • Record reviewer, timestamp, gate IDs, results, and evidence links; exclude secrets, tokens, PII, and raw identity-provider responses.

Stage 5 · Release and remaining acceptance gates

  1. Confirm the approved client account, least-privilege deployment roles, private state, alert destination, network allowlist, and immutable release artifact.
  2. Publish certificate-validation DNS records and register exact callback and post-logout URIs with the approved identity provider.
  3. Review the plan and obtain explicit operator approval before apply. Verify health, routing, cookie properties, real provider login/logout, stable subject ownership, replay/state/nonce rejection, and unauthenticated HTTP/WebSocket denial.
  4. Run the usability protocol and acceptance threshold defined by the client specification. Keep aggregate evidence only; synthetic tests do not satisfy human acceptance.
  5. Complete end-to-end disposal and forced-failure proof before claiming the configured expiry requirement is verified.
