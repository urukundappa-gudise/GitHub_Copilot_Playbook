01 / Identity provider

Microsoft Entra portal

Use the InfoVision tenant and one app registration for this relying application. The backend discovers tenant-specific OIDC endpoints and requests openid profile email. It does not call Microsoft Graph, so no Graph API permission is required by this flow.

Create or select the app registration

In Microsoft Entra admin center → Identity → Applications → App registrations, select the AIMPLIFY registration or create one. For employee-only access, select accounts in this organizational directory (single tenant), subject to InfoVision identity-admin policy.

Copy the application identifiers

From the registration's Overview, copy Directory (tenant) ID into AZURE_AD_TENANT_ID and Application (client) ID into AZURE_AD_CLIENT_ID. These are identifiers, not credentials.

Configure Web redirect URIs

Under Authentication → Add a platform → Web, add the exact callback and post-logout URLs for the environment. The two localhost URLs below are for the current local port settings; production URLs are different.

Create a client secret

Under Certificates & secrets → Client secrets → New client secret, create a secret according to organizational expiry policy. Copy its Value, not its Secret ID. Entra shows the value only once. Store it locally in .env or create a raw-string secret in AWS Secrets Manager for ECS.

Check token claims

The backend requires ID-token claims oid, upn, and name; email is optional. In Token configuration, verify the tenant emits upn and name in the ID token. If needed and approved, add upn as an optional ID-token claim. The authorization subject is the stable oid, not email or UPN.

03 / Cloud runtime

AWS portal configuration

The active GitHub Actions workflow deploys ECS Express. The App Runner Terraform root is retained separately and is not the active workflow. Local SSO does not need AWS; the following is for production deployment.

Terraform ownership: Use the AWS console for account prerequisites, Terraform state bucket, and Secrets Manager values. The repository's bootstrap and service Terraform create/manage the ECR, VPC/subnets, ECS cluster, roles, and ECS Express service. Avoid manually creating duplicate resources or broad IAM permissions.

Choose account and region

Record the AWS account ID and one region for ECR, ECS Express, Secrets Manager, and Terraform state. Set the GitHub variable AWS_REGION to that same region.

Prepare Terraform state bucket

Provision the S3 bucket before Terraform init. In AWS S3, block all public access, enable encryption and versioning, and retain state. The workflow uses S3 lockfiles. Do not store AWS keys or Entra secret values in the bucket manually.

Verify GitHub Actions OIDC provider

In IAM → Identity providers, verify provider URL https://token.actions.githubusercontent.com with audience sts.amazonaws.com. The bootstrap Terraform creates the repository/ref-scoped deployment role. Its trust must match the exact repository and main ref; immutable owner/repository IDs are preferred.

Create Secrets Manager values

Create a secret for the Entra client secret as a plain raw string (not a JSON object). Record only its ARN for deployment. For production ECS, create a second raw-string secret containing the PostgreSQL connection URL and record its ARN. Never put either secret value in GitHub variables, Terraform variables, shell history, or this report.

Apply bootstrap infrastructure

Apply deploy/bootstrap with enable_ecs_express=true and the exact secret ARNs. Terraform creates the ECR repository, GitHub deployment role, ECS cluster/VPC/public subnets, execution role, infrastructure role, and scoped access to the configured secrets. Review the plan before applying and retain state keys.

Configure the service and database

Use a shared PostgreSQL database for production; apply the Alembic chain through 0003_oidc_sessions before routing users. Ensure ECS tasks have approved network/TLS access to the database and Secrets Manager. In ECS Express the execution role reads only the configured secret ARNs.

Set production identity URLs

Use a stable HTTPS custom domain when possible. Otherwise obtain the public ingress hostname from the ECS Express deployment. Set APP_ORIGIN to the exact origin without a trailing slash; set callback and post-logout URLs to paths on that same host; register both in Entra before production sign-in.

05 / URL alignment

Production URL values must agree

Let https://<approved-host> be the exact public ECS Express origin (or approved custom domain):

APP_ORIGIN=https://<approved-host>
AZURE_AD_REDIRECT_URI=https://<approved-host>/api/v1/auth/callback
AZURE_AD_POST_LOGOUT_REDIRECT_URI=https://<approved-host>/login
  • Register callback and post-logout URLs as Web redirect URIs in Entra.
  • Use the exact hostname, HTTPS scheme, and paths in GitHub variables.
  • Set DEPLOYMENT_ENVIRONMENT=production.
  • Set AUTH_REQUIRED=true and AUTH_MOCK_MODE=false.
  • Set a production APP_ORIGIN without a trailing slash.
  • Use client-secret and DB URL secret ARNs from Secrets Manager.
  • Apply the OIDC session database migration before release.
  • Redeploy ECS tasks after rotating either runtime secret.

If the final public hostname is not known before service creation, choose a stable custom domain or provision the service to obtain its ingress host, then register the exact URLs and apply the production configuration. Do not guess or register a different URL.

06 / Acceptance

End-to-end verification

Local app

Run .run.ps1 from the repository root and open http://localhost:5174/login. Click the InfoVision SSO button. The browser should navigate to https://login.microsoftonline.com/<tenant>/oauth2/v2.0/authorize. Do not paste the full authorization URL into a ticket: it carries protocol state.

Callback and session

After successful sign-in, Entra returns to /api/v1/auth/callback; the app validates signature, issuer, audience, expiry, state, nonce, and PKCE before setting an HttpOnly, Secure, SameSite=Lax oidc_session. The UI should display the verified employee name and UPN.

Session endpoint

Before login, GET /api/v1/auth/session should return 401 and header X-Authentication-Required: true. After login, it should return 200 with authenticated status. Do not log or publish response cookies or tokens.

Production release

Confirm ECS Express is healthy, deployed the intended commit SHA, has secret injection and PostgreSQL connectivity, and returns the same auth/session behavior over its HTTPS ingress. A local test does not prove AWS release health.
